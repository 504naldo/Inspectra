# Inspectra — Claude Code Guidelines

## Git Workflow

1. **Develop on the assigned feature branch** (e.g. `claude/enable-shared-drive-browsing-nNO52`).
2. **Commit** with clear, descriptive messages.
3. **Push the feature branch** to `origin`.
4. **Immediately merge into `main`** and push `main`:
   ```bash
   git checkout main
   git pull origin main
   git merge --no-ff <feature-branch> -m "<commit message>"
   git push origin main
   ```
5. Every session ends with `main` reflecting all completed work — no changes stay only on a feature branch.

## Stack

- **Frontend**: React 19 + Vite, TypeScript, Tailwind CSS v4, shadcn/ui, tRPC client
- **Backend**: Express + tRPC server, Drizzle ORM (MySQL/PlanetScale), S3/R2 storage
- **PDF**: PDFKit (server-side, async pre-fetch pattern for images)
- **Auth**: Google OAuth via `jose`
- **Deploy**: Railway (auto-deploys on `main` push)

## Database Migrations

There are two parallel migration histories — this is intentional, not drift to "fix":

- **`drizzle/*.sql`** (tracked by `drizzle/meta/_journal.json`) is generated by `drizzle-kit generate` straight from `drizzle/schema.ts`. Running `npx drizzle-kit migrate` against an empty database brings it to the *current* schema in one shot — this is what CI uses.
- **`drizzle/migrations/*.sql`** is the hand-written, sequentially numbered record of every change actually applied to the live Railway/PlanetScale database, because PlanetScale can't run `drizzle-kit migrate`-style multi-statement/transactional migrations. After merging a schema change, write the next-numbered file here and run it manually on Railway (additive, non-destructive statements only).
- **`drizzle/migrations/RAILWAY_CATCHUP.sql`** is a consolidated, idempotent (`IF NOT EXISTS`-guarded) replay of the manual history, meant to bring an already-partially-migrated production database up to date. Its `IF NOT EXISTS` ALTER syntax is a MariaDB extension — it will fail on vanilla MySQL. Don't use it against a fresh database (CI or local); `drizzle-kit migrate` alone is sufficient there since the journal already reflects the full current schema.
- A few columns (e.g. `users.sessionVersion`) are deliberately *not* declared in `schema.ts` and only exist via the manual migrations — see the comment in `drizzle/schema.ts` near the `users` table. Code that touches them does so defensively: writes go through raw SQL wrapped in best-effort try/catch (e.g. `incrementUserSessionVersion` in `db.ts`, which swallows the "Unknown column" error CI raises since its journal omits the column), and reads cast + default (`(user as any).sessionVersion ?? 1`). As a result these paths no longer produce failing tests on the journal-only CI database — the logout/session suite passes. (Local runs without `DATABASE_URL` still fail the *integration* tests that need a real MySQL, e.g. `siteDetails*.test.ts`; that's an environment limitation, not a regression — CI provisions `mysql:8`.)

CI (`.github/workflows/ci.yml`) provisions a fresh `mysql:8` service container and runs only `npx drizzle-kit migrate` — real MySQL is required (not MariaDB) because MariaDB's `JSON` type is a `LONGTEXT` alias and the mysql2 driver won't auto-parse JSON columns read back from it, breaking any test that round-trips a `json()` column.

## Key Conventions

- tRPC procedures: `protectedProcedure`, `officeProcedure`, `technicianProcedure`, `adminOrOfficeProcedure`
- Finalized jobs (`finalizedAt != null`) are immutable — all mutations must check this first
- PDF generators must pre-fetch all async resources (images, signatures) **before** entering the synchronous `new Promise` PDFKit callback
